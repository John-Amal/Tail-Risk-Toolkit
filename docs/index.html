A flood and a portfolio loss have the same mathematics

Ask a hydrologist for a 100-year flood level and a risk manager for a 99% Value-at-Risk and you get the same object: a quantile of a distribution fitted to the few observations that exceeded a high threshold. Only the vocabulary differs.

Peaks-over-threshold modelling makes that concrete. Take everything above a threshold u, fit a generalised Pareto distribution to the excesses, and the tail becomes

P(X > z) = ζu · [1 + ξ (z − u) / σ]−1/ξ

Invert it at 1 − q and you have Value-at-Risk. Invert it at 1/T and you have a return level. One estimator, two professions. This toolkit hands both to an agent, along with the diagnostics that decide whether the fit deserves to be trusted.

A session, end to end

Four questions, four tool calls. The output below is real — every figure on this page comes from running the toolkit on the sample in the chart above.

First

Is the threshold defensible?

“Before we trust any tail estimate, check whether the fit is stable.”

Threshold choice is the one genuinely subjective step in a POT analysis, so the toolkit makes an agent confront it first. If the shape parameter drifts as the threshold rises, the fit has not reached the regime where the theory applies. Here it holds to within 0.10 across the sweep.

tailrisk_threshold_stability

Then

How heavy is the tail?

“Fit the tail and tell me what the shape parameter means.”

The shape parameter ξ is the headline. Above zero the tail is unbounded and no amount of history reveals the worst case; below zero there is a finite ceiling. At — this sample is heavy-tailed, which is the formal reason a normal model will understate it.

tailrisk_fit_gpd

Then

What is the loss at the far end?

“Give me the 99.9% VaR and Expected Shortfall, and show me what a normal assumption would have said.”

Three estimates come back together, because the gap between them is the answer. Historical simulation cannot exceed the largest loss ever observed, so it stops working exactly where the question gets interesting. The Gaussian figure is the one that gets people into trouble.

tailrisk_var_es

Finally

Does the model hold up out of sample?

“Backtest it. Would a regulator accept this?”

Every forecast is fitted on trailing data only, then compared with the next realised loss. The Kupiec test asks whether breaches happen at the right rate; the Christoffersen test asks whether they arrive independently rather than in clusters. Passing the first and failing the second is the signature of a model that reacts too slowly to volatility.

tailrisk_backtest_var

The six tools

All read-only and side-effect free. A series arrives inline in the conversation or gets read from a local CSV; nothing is written back.

tailrisk_fit_gpd

Fits a generalised Pareto distribution to threshold exceedances and reports the shape, scale and exceedance count, with a plain reading of what the shape implies.

tailrisk_var_es

Value-at-Risk and Expected Shortfall by extreme value theory, historical simulation and a Gaussian baseline, returned side by side with the ratio between them.

tailrisk_return_level

The level exceeded once per return period, with the equivalent VaR confidence, for when the question arrives as a 1-in-N event rather than a percentage.

tailrisk_backtest_var

Rolling-window, strictly out-of-sample backtest with Kupiec, Christoffersen and conditional coverage statistics, plus a verdict in words.

tailrisk_threshold_stability

Refits across candidate thresholds so the agent can see whether the estimate is in the asymptotic regime before quoting a number from it.

tailrisk_load_csv_series

Reads one numeric column from a local file, counting the rows it had to skip so data quality stays visible rather than silently absorbed.

Run it

Python 3.10 or newer, and version 2 of the MCP SDK.

install
git clone https://github.com/John-Amal/Tail-Risk-Toolkit.git
cd Tail-Risk-Toolkit
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
pytest

The suite simulates from distributions with known tails and checks the estimators recover them, so a pass means the maths is right, not merely that the code ran.

connect an MCP client
{
  "mcpServers": {
    "tailrisk": {
      "command": "/path/to/Tail-Risk-Toolkit/.venv/bin/python",
      "args": ["-m", "tailrisk_mcp.server"]
    }
  }
}

The server speaks stdio. Switch the transport to streamable-http in server.py to run it remotely.

What it does not do

  • Observations are treated as independent and identically distributed. Real returns cluster in volatility, so a production version would filter with a GARCH model and fit the tail to standardised residuals, following McNeil and Frey. This one fits the raw series.
  • Parameter uncertainty is not propagated. There are no confidence intervals on VaR, Expected Shortfall or return levels; a profile likelihood or a bootstrap over the exceedances would be the next addition.
  • Nothing here is multivariate, so portfolio aggregation across dependent risk factors is out of scope.

Each of these is a known gap rather than a discovered one, which is the only honest way to ship a statistical tool.
